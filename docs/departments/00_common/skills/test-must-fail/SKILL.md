# 検査は「落ちること」を1回見てから置く

## なぜ要るのか
改修ログ736行のうち **61件**が「検査を足したが落ちない/写像を変えたのにテストが旧前提」の型だった。
**常にPASSする検査は、検査していないのと同じ**で、しかも「守られている」という誤った安心を配る。
これは沈黙の事故=最悪の形だ。

## 手順(順番を変えない)

1. **★0歩目= 壊れている側を1回見る。** 検査を書く前に、いま実際に壊れている実物(または
   わざと壊した入力)を用意する。後の比較対象がこれになる。
2. **検査を書く。**
3. **★落ちることを見る。** わざと壊した状態で走らせ、**FAILの文字を目で見る**。
   FAILしないなら検査が間違っている=実装ではなく**検査の妥当性を先に疑う**。
   よくある空PASSの原因= 対象ファイルが見つからず0件で回った / try-except が握り潰した /
   条件が常に真 / 実行はされたが assert が無い。
4. **直す(または元に戻す)。**
5. **PASSすることを見る。** 落ちる→直る の**両方**を見て初めて、その検査は生きている。

## 走らせ方(このプロジェクト)
- JS= `node tests/test_xxx.js`(例 `tests/test_idb_failopen.js`)
- Python= `python tests/test_xxx.py` / 常駐まわりは `python scripts/_daemons/test_daemon_keeper.py`
- 部門横断の一括点検= `python docs/departments/qa-reviewer/checks/run_all.py`

## 写像・判定を変えた時の追加規則
- ★**その写像を読むテストまで一緒に動かす。** 片側だけ直すと、テストは旧前提のままPASSし続ける。
- ★**共有される関数に条件を足したら、呼び出し元を全部数える。**
  「この経路は別なので影響なし」と書いたなら、**その主張こそ数え直す**。
- 既にある検査ツールを使う(`bump.mjs --check` / `registry_tool.py --check` / `status.ps1`)。
  **その場のワンライナーで数え直さない**——毎回違う嘘をつく。

## 報告の言い方
- 「検査を足した」だけなら **入れた(確認待ち)**。
- 「落ちるのを見た/直ってPASSした」まで行って **効いた**。
- **症状が出ていたのと同じ場面**の実物を見るまで **直った** と書かない(§4.55)。
