## 何を止めるか(1行)
**共有状態(前景画像・一覧DOM・録画Blob・作品情報の行など「後から非同期に書き込む先」)へ、複数の非同期継続が"世代照合なし"で書き込むと、遅く完了した古い応答が新しい状態を上書きする。** ボタン連打・タブ切替・アカウント切替・遅い変換が絡むと「前に使った画像が残る」「別作品のURLに化ける」「黒い無言箱」になる。**解法は毎回同じ(世代番号を採番→書く直前に最新世代か確認→古ければ捨てる)なのに、事故のたびに別の関数で作り直している。**

## 不変条件(守れているか機械で見る)
- **I1**: 共有状態(前景画像・一覧・録画Blob・作品情報行など、UIが後で読む先)へ**非同期継続(then/await/onload/コールバック)から書き込む処理は、書く直前に世代番号を照合する**。採番(発行時に`gen++`を控える)→書く直前に`myGen===currentGen`を確認→違えば破棄、を対で書く。
- **I2**: 世代照合は**書き込みの直前**に置く(取得の開始時だけの確認では、取得中に世代が進んだ遅着を防げない)。fail方向=**古い世代は静かに捨てる**(上書きより破棄が安全)。
- **I3**: 同じ状態に**別々の世代カウンタを増やさない**=その状態の世代は1本。切替(アカウント/タブ/作品)で世代を進める入口も1つに束ねる(INC-138/135と同型の分裂を防ぐ)。

## 機械で見る案(改修αへ渡す検査の下書き)
- ★**grep一発では不可**=`onload`代入や`then`は正当な使い方が大多数で、有無だけでは撃てない。だから**「世代管理が必須の書き込み先」の登録簿(ベースラインJSON)**を持つ方式にする(番犬型・CSS波及型と同じ「新規混入だけ止める」思想):
```
# 世代照合が要る共有状態への書き込み関数を registry(baseline.json)へ列挙する。
# 例: setForeground / renderStockList / commitRecordingBlob / applyWorkInfoRow ...
# 検査= 登録簿の各関数の本体に「世代番号の採番と、書く直前の照合(myGen===currentGen 等)」が
#       両方在ることをassert。片方でも欠けたら赤。登録簿に無い新規の共有状態書き込みが
#       増えたら「世代管理の要否を判定して登録簿へ追記せよ」と警告する。
```
検査の芯= **「世代照合が要る書き込みで、照合が欠けたら赤 / 新しい共有状態書き込みは登録簿で要否を明示させる」**。既存は登録簿へ据え置き=回帰ゼロ。

## 直し方の定型(共有状態へ非同期で書く人がやること)
1. 書き込み先の「世代」を**1本**決める(状態ごとに1カウンタ)。切替・再取得で`gen++`。
2. 非同期を発行する時に`const myGen = gen`を控える。
3. **書く直前**に`if (myGen !== gen) return;`(古い応答は捨てる)。
4. 同じ状態へ別経路からも書くなら、その経路も同じ`gen`を見る(カウンタを増やさない)。
