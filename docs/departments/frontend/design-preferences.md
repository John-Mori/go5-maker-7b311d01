## 1. 絶対規約(破ると"直された"になる・最優先)

- **「よくあるClaudeの紫デザイン」を使わない(恒久・Chami指示2026-07-03)。** モーダル/オーバーレイ/
  ボタン等の新規UIに紫を使わない。禁止色の例: `#5b3f8e / #2a1a4e / #1a1a2e / #d4b3ff / #c4a0ff`。
  → アプリ配色(§2)に合わせる。※アカウントテーマの紫(月詠み=#241a3d 等)は**別枠でOK**。
- **UI文言の括弧は必ず半角 `()`。全角 `()` 禁止**(CLAUDE.md・system-engineer BOOT)。
- **時刻表示は日本時間(JST)**。`toISOString()`/UTCをそのまま表示に出さない(Chamiの体感と9hズレる)。
  JSは端末ローカル(`getHours()`等)。例外=Cloudflare枠リセット等のUTC固定値は集計UTC・表示JST併記。
- **座標系を崩さない(§3)。** px/vh/vw を直接使わない。プレビューと書き出しは同一Canvas・同一式。
- **締めの言葉に「刻んだ」系を使わない**(2026-07-16・全キャラ廃止)。記録は「(自然な完了の言葉)。(ファイル名)」。

## 3. 座標系(動画Canvasの最重要規約・崩さない)

- 基準フレーム **W=1080 / H=1920(9:16)が唯一の基準座標系**。`<canvas width height>` も一致。
- 位置・フォントサイズは `H×係数` / `W×係数`。旧絶対px定数は `U(v)=v*H/1280` で換算。
- **プレビューも書き出しも同一Canvasに同じ式で描画** → PC/スマホ/書き出しで一致(CSSは9:16を一様縮小表示するだけ)。
- 縦オフセットは `OFF` オブジェクトで一元管理(`OFF.whole`/`OFF.textAuthor|Detail|Title`等)。
- `document.fonts.ready` 後に再描画(フォールバックフォント計測ズレ防止)。

## 5. モバイル/レイアウト

- **iPhone/iPad のブラウザ最優先。縦型 9:16。** スマホで横潰れしない(CSSの9:16固定を崩さない)。
- タブ構成の実績: 🎬動画作成 / 📅カレンダー / 🦋投稿 / 🔗アフィリンク(iframe埋め込みでCSS/JS衝突回避)。
- キャッシュ運用: アセット参照は `app.js?v=N`。中身を変えたら **`node scripts/bump.mjs` で一括バンプ**(手動sed禁止)。
- ★**長い一覧はページ分けして描画する**(全カードを一度に描かない・既定30件/選択可)。iOS Safariは画像を大量デコードすると下の方のサムネ/プレビューが表示されなくなる=投稿量が増えても見える形に。候補タブ・投稿履歴で**同一方式に揃える**(v=886・8/22窓で確定)。
- ★**同種の一覧タブには同じ機能を揃える**(検索・絞り込み等)。片方のタブだけ検索UIが無い=構造欠落として埋める(全候補タブに検索を後付けした 8/22窓)。Chamiは「同じような画面なら同じ操作ができる」ことを当然に期待する。
- ★**情報は"見ないもの"を出さない**=投稿履歴に「動画生成で使った画像」は出さない(Chami「見てないしいらない・読み込み省略」)。プレビュー枠は本物の仕上がりプレビューだけに限定し、生成画像を混ぜない。**密度より、要るものだけ**。
- ★**文字は端末に勝手に拡大させない＋平滑化して滑らかに出す**(commit 9edeeed・Chami依頼2026-08-31)。iOS Safariは横向き時に本文を自動拡大して、詰めて組んだ座標/レイアウトを崩す=`text-size-adjust:100%`(webkit接頭辞併記)で止める。加えて `-webkit-font-smoothing:antialiased` / `-moz-osx-font-smoothing:grayscale` でWebKit/Firefoxの文字を滑らかに。→ **形は一切変えず見た目だけ整える**のが好み(字形・座標・レイアウトは触らず、拡大の乱れとギザつきだけ抑える)。全ページ共通で `html,body` に効かせる。
- ★**画像ズームの表示サイズは元画像の大きさに引きずらせない=一定の表示枠に収める**(commit 9874f87・Chami依頼2026-09-02)。動画生成用画像のズーム(通常/使用済み/除外のラジオを出すもの)で、縦長(9:16)の元画像が中央寄せで上端がラジオ(top:96px)へ食い込み「元が大きいと表示が大きすぎる」に見えた=ラジオ表示時のみ `.fz-zoom.has-mark` を付けて `max-height` を 88vh→76vh へ絞り、ラジオ帯の上とカウンタの下に余白を残す高さに収める。横長(既に~62vh)は不変。→ **表示は枠に収めたい(元の大きさで大きく出しすぎない)/問題が出ている縦長だけを最小で直し、既に収まっているものは触らない**のが好み(§149「形は変えず見た目だけ整える」と同系)。

### ★ C-005 端末設計前提(2026-07-22 Chami確定・裁定A/C-005 登録済み)

> **投稿導線はスマホ1台で完結する。端末をまたぐ前提の設計をしない。**

**根拠(固い構造的制約・気分で変わらない):**
- YouTube Shortsで許諾音楽を付けられるのはスマホアプリからのみ(著作権許諾経路の制約)。
- 動画生成→投稿完了まで一連の流れ。途中で端末を変えるメリットがない。
- よって「スマホ前提」は設計の確定前提として使ってよい。

**★ 適用外(取り違え禁止):**
- **「書き込み」=スマホ1台で完結してよい**。
- **「表示(履歴閲覧)」=全端末で見えなければならない**。これは別の話。
  - `displayItems_()` のシート補完は**維持**。落とさない・弱めない。
  - シートを正本にする意味=「どの端末から見ても履歴が見える」こと(INC-112 の再発防止)。
  - 「端末をまたがないなら表示も端末ローカルで足りる」は**誤読**。

**実装に転換する時のチェック:**
1. 書き込み経路か表示経路かを最初に区別する。
2. シート補完(`displayItems_()`)を弱める変更は C-005 では正当化されない。

## 5.9 承認プロセス(C-006 発効済み・2026-07-22)

> **フロントのpushは承認不要で実行してよい。(裁定 C-006)**
> Chami原文:「なんならプッシュデプロイまで済ませておいてほしい」

**承認不要で実行できる作業:**
- 読み取り・影響範囲の測定
- 部門間の連絡と報告(send message / dispatch / 返信)
- `docs/` 配下の下書き
- **フロントのpush**
- GAS/Workerのデプロイ

**★適用外(今まで通り上申する):**
- **削除**(裁定 C-003。ファイル・行問わず消さない。退避は可)
- 本番データの書き換え・移行
- 設定変更(権限・トリガー・シークレット・registry)

**★誤読防止:**

**★link-worker に注意:**
