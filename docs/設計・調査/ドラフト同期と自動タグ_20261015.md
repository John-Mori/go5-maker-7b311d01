# ドラフト同期と動画の自動タグ — 原因・修正・検証

対象: `John-Mori/go5-maker-7b311d01`。調査基点は `origin/main` の `b74c81f`、フロント v1030。
作業枝: `codex-draft-tag`。指定のworktreeでfetch後にmainへ土台を合わせた。本番へのpush/deployは行っていない。

## 1. ドラフト同期の根本原因

ドラフトのキーは同期対象に登録されていた。漏れていたのは許可リストではなく、進行と競合解決の設計だった。

| 条件 | v1030の動作 | 結果と導入履歴 |
| --- | --- | --- |
| IDB画像走査・画像送信が未完了 | `syncOnce` が `Promise.all([secStep,candMirrorStep,idbStep])` の後で初めて状態をpull | 文字だけの一覧・投稿編集も止まる。候補だけは `598ea6b` (2026-08-25) で独立経路に移ったがドラフトは残った |
| AとBが別々のドラフトを編集 | `go5_stock_meta` をidでunionするが、同一idの優先側は配列全体の `t` で選ぶ | Bの別作品の保存で、Bが持つ古いA作品も勝つ。`f9e7d6f` (2026-08-01) が候補の配列統合をドラフトへ適用した時から存在 |
| 2台のpushが同じversionを読む | Workerがversion比較後に無条件 `R2.put` | 両方成功を返して片方の状態を消す。`263736e` (2026-08-27) のR2移行で導入 |
| R2の読取障害 | 例外を握り、旧KVまたはemptyへ戻る | 障害を新規状態と誤認し、古い状態を正本へ上書きできる。同じ `263736e` |
| 同期union後に一覧が21件以上 | 次の保存で `slice(0,20)`。容量不足ではさらに古い行をpopして成功扱い | 端末で消失し、雲から再出現する。20件上限は `244d546` (2026-07-27)、quota時の縮退は `ba9cca9` (2026-08-16) |

### 再現するキーと順序

1. Aの生成完了を `video-created` で受け、動画保存を確認後に `go5_stock_meta=[D1]` を保存する。
2. `stock:imgs:<id>` などのIDB走査を未解決にすると、旧全同期はpull前で停止する。Aの `go5_stock_meta` は存在するが、WorkerとBにはない。保存直後のflushを増やしても同じ `_busy` に阻まれる。
3. 通信できる場合も、A/Bが `[D1旧,D2旧]` を受信した後、AがD1を編集し、BがD2を後から編集すると、Bの配列時刻が新しくなる。B→Aの順で同期するとD1まで旧値へ戻る。
4. 投稿モーダルの編集は `go5_draft_post_<id>` に別保存される。これは既存のキー単位LWWで、一覧の時刻とは別。受信した時計より遅い端末の編集・削除にも単調な時刻が必要になる。
5. 削除は `go5_stock_del[id]` の墓標、一覧からの除外、`go5_draft_post_<id>` の削除で構成される。墓標を失う、または一覧だけ送ると古い端末のunionで復活する。復元だけは `addedAt > tombstone` として明示的に復活させる。
6. Workerでは2pushを同時に到着させると、旧実装は双方が同じversionを確認して双方成功する。R2読取例外時も旧実装は503にならず、古いKV/emptyを返す。いずれもWorker本体を使った試験で修正前の失敗を確認した。

### 過去の修正で再発を止められなかった理由

`git log --grep`、`git log -S`、各commitの差分を確認した。

- `945b8b5` (08-03): 保存時flush。送信開始は早まるが画像待ちと配列単位LWWは残る。
- `c8c7a97` (08-04): pageshow/focus/onlineで即pull。受信の機会を増やす修正で、競合単位は変わらない。
- `70cec63` (08-06): 後着画像で再描画。通信前の停止を解消しない。
- `837440f` (08-13): Stock.htmlのアカウント判定と描画時のIDB待ちを修正。同期処理自身のIDB待ちは残る。
- `95670e2` (08-18): 履歴サムネを軽量化。容量圧迫は減るが、上限で行を消す構造は残る。
- `4f23ae5` (10-12): 通信timeoutと全同期の見張り。停止からは戻れても、文字情報を画像より先には送らない。
- `9839c04` / `a50c2e8` (10-13): 保存時刻・保存時の同期予約・受信値の時刻を修正。配列の保存時刻なので別idへの巻き添えは防げない。

## 2. 自動タグの根本原因

判定の正本は `core/movie-attrs-core.js` → `core/categories.js`。実際にチェックボックスへ適用するのは `js/bluesky.js` の `applyAttrsInput_` だった。`js/app.js` の候補遷移は `Go5MovieAttrs.applyGenres`、作品URL・ウィザードは作品情報取得後の `autoApplyAttrsFromInfo_` を通る。

1. 候補の `genres/title/ai` でハーレム・総集編・AIをONにする。
2. 同じ作品の取得結果が `genres:[] / partial:true` で後着する。旧適用処理は全カテゴリを判定結果へ置換し、ハーレム・総集編などをOFFにする。AIだけの例外保護では他タグを守れない。
3. この後 `movie_auto_attrs_cid` が保存され、同じcidの再適用を抑止する。作品情報キャッシュもtitleがあれば部分情報を成功扱いし、再取得しない。
4. 別タブにも同じlocalStorageの `movie_auto_attrs_cid` が見える。Aタブが適用した後、まだチェックのないBタブも「適用済み」でreturnする。DOMは共有されていない。

履歴上、共有cidガードは `443de99` (2026-07-14) の初期実装で導入された。候補のタグが後着の空情報で消える経路は、`252944c` (2026-08-04) が候補側のcidガードを外して再取得結果の適用を通した時から成立する。その変更はfloorからAIを拾うための修正だったが、部分取得を「全タグ非該当」とする適用方式が残った。

`fb3a794` のreload時解除、`e55b4c8` の判定一本化、`921a988` の未確認AI保護、`ccc1afd` のAI規則更新は、それぞれの判定・取得経路を改善したが、共有ガードと全置換を解消しない。通常の候補遷移・URL取得ではタグが付くことも確認した。全作品で常時壊れる不具合ではない。

今回確認できたのは上記条件の再現と導入commitである。Chamiの報告時の実データ・実ブラウザログは取得していないため、その瞬間にどちらの条件が起きたかと発症日時は不明。

## 3. 改善案と実装

既存のキーとWorkerの状態形式を維持し、ドラフト文字情報の進行・競合解決・適用状態を、それぞれ扱うデータの単位へ揃えた。

| ファイル | 実装 |
| --- | --- |
| `core/sync.js` | `syncDraftsNow` を追加。画像走査を待たずに一覧/履歴/投稿編集/墓標をpull・merge・push。全同期との二重適用を除去 |
| 同上 | 変更した行だけ `_syncAt` を進め、idごとに競合解決。旧行は初回の時刻を固定。投稿編集も受信済み時刻を越えて保存・削除する |
| 同上 | 削除墓標をunionして適用。inlineサムネは通信と専用snapshotから除外。受信保存が失敗したキーはsnapshotを進めず、容量回復後に再取得 |
| 同上 | 同時実行を1本にまとめ、競合時に最大3回再pull。45秒で待ちを打ち切り、古い応答の適用を無効化。既存のAbortController付きAPI通信を使用 |
| `sync-worker/src/index.js` | R2 ETagの条件付きPUTでversion確認後の競合を検出。初回作成・KV移行も存在しない時だけPUT。読取障害は503で保持。8MiB上限をUTF-8の実バイト数で判定 |
| `js/stock.js` | 現役ドラフトの20件切捨て・容量時の行削減を撤去。削除は墓標成功後だけ本体blobを処理。復元は保存先の成功前に履歴を消さない。再作成のタグ選択を適用状態へ復元 |
| `js/bluesky.js` | 適用状態をタブ内・作品単位に変更。検出したタグを合流し、手動ON/OFFを保持。部分情報は再取得可能にし、作品切替直後の旧応答を破棄 |
| `js/categories-ui.js` | チェック欄の再描画を通知し、先に届いた判定結果を新しいDOMへ反映 |
| `scripts/sync_decisions.json` | 一覧・履歴・投稿編集の同期方針を実装と一致させた。同期対象キーの追加なし |
| `tests/helpers/sync-worker.cjs` | Worker本体を実行するメモリR2。テスト専用認証、条件付きPUT、読取障害を再現 |
| `sync-worker/test_state_conflicts.mjs` / `tests/test_sync_state_conflicts.mjs` | 初回/既存状態の同時push、読取障害の4試験。既存CIのtests/test_*入口にも接続 |
| `tests/e2e/draft-sync-tags.spec.js` | 独立localStorageの2contextと同一Workerによる10試験 |
| `tests/test_categories_ai.js` | 保護分岐の文字列検査を、実際の適用コードによる部分情報・遅着AI・別タブ・手動指定・再作成の試験へ置換 |
| `tests/test_sync_save_kicks.js` | 保存予約の本数に新しい45秒見張りを含めないよう、実際の予約期間3〜10秒を検査 |
| `tests/test_sync_worker_r2_state.js` | 読取不能をempty成功にしない期待へ更新。R2のみの新規作成・KV移行も維持 |

R2の条件付きPUTの仕様は [Cloudflare公式Workers API reference](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) の `onlyIf` / `etagMatches` / `etagDoesNotMatch` と、条件不成立時のnull応答を参照した。

版上げは `node scripts/bump.mjs` を1回実行し、v1030からv1031へ更新した。対象は `index.html`, `KouhoLists.html`, `KouhoTeian.html`, `analytics.html`, `Stock.html`, `StockLists.html` の217参照。scheduleのstampも再生成され、内容差分はなかった。CIの番犬10本は全成功、exit 0。

## 5. 窓口の本番確認

Workerの修正版を先に反映し、フロントを反映後、検証する全端末/タブを新版へ再読み込みする。旧版の開きっぱなしタブは旧競合規則で書き込むため、混在させない。

1. 同じ同期設定・チャンネルの端末A/Bを用意する。Aの動画作成画面で1件をドラフト保存し、Bの `Stock.html` に同じIDのカードが出ることを確認する。設定画面の同期エラーがないことも見る。
2. Aの投稿モードでYouTube説明欄を編集し、Bで開き直して同じ文を確認する。AとBで別作品を編集して往復同期し、どちらの編集も残ることを確認する。
3. Aでそのドラフトを削除し、Bでも消えることを確認する。Bを再同期/再読み込みしても戻らないこと、作成履歴から明示復元した作品は両方へ戻ることを確認する。
4. 画像が遅い端末でも一覧と投稿編集が先に届くことを確認する。動画の再生/DLとサムネの到着は、文字の同期とは別に実物で確認する。
5. タグ付き候補から動画作成へ進み、作品情報取得前後でハーレム・総集編・AIなどが消えないことを確認する。手動で外したタグが戻らないことも確認する。
6. 2タブを先に開き、同じ作品URLをA→Bの順で入力する。両方にタグが付き、別作品へ切り替えると前作のタグを持ち越さないことを確認する。

## 6. 適用範囲と残る制約

- 本番への反映と実機iPhone Safari確認は窓口の工程。ローカル試験の成功を本番復旧とは扱わない。
- 既に全端末/雲から失われたドラフトをこの修正だけで復元することはできない。過去データの残存状況は未調査。
- 行の競合はid単位、投稿編集は投稿id単位のLWW。同じ作品の同じ情報をオフラインで同時編集した場合、両方の文章を保存する共同編集機能ではない。未観測の同時編集には端末時刻差が影響する。
- 通信は既存のstate blob全体とversionを使う。行ごとの時刻は追加したが、サーバを差分APIへ移行したわけではない。8MiBの状態上限と端末localStorageの容量上限は残り、超過はエラーにしてデータを保持する。
- R2設定のある本番構成で条件付きPUTを保証する。旧KVのみの構成は互換経路のままで、同じ原子性は保証しない。R2未作成かつ旧KVを読めない場合も503とし、空の正本で旧データを消す初期化は行わない。
- 作成履歴の既存30件上限/古いblob整理と、明示purge用墓標の既存保管期間は今回変更していない。現役ドラフトの20件切捨てとは別の履歴保存仕様として残る。
- 自動タグは同一作品から得た肯定情報を保持する。後の空応答だけでは外さない。判定が誤っていた場合は手動で外せる。
