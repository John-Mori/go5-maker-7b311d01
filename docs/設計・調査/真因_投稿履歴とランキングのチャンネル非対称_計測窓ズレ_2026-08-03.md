## 0. 結論の要約

このクラスタは「個々のバグ」ではなく、**同じ1つの構造欠陥が別の顔で再発し続けている**。

> **表示の正本が「端末localStorage」で、シート(サーバー)は"補完"扱い。
> その補完チェーンが 揮発キャッシュ×JSONP×TTL×表示ガード の4段直列で、
> しかも acc1/acc2 でこのチェーンへの依存度が違う。**

- acc1(月詠み)は古い投稿もこの端末のlocalStorageに実在する → 補完チェーンが死んでも表示は無傷。
- acc2(宵桜)の7/29以前は**この端末のローカルに(ほぼ)無く、シート補完チェーンでしか出ない** → チェーンのどこか1段が欠けるたびに「また消えた」。
- v574(表示ガードfail-open)→v578(SWR退避)→v575/576/579/580/581(ランキング供給)と、**チェーンの各段を1つずつ塞いできた歴史そのものが再発の証拠**。段はまだ残っている(§2.1)。

計測窓ズレは別系統だが同型の病:**観測系が3つ併存**(クライアント`view_snaps`/GAS`時点記録`/GAS`snapshot.gs`)し、許容窓の規約がバラバラ(+50% / +9分 / ティア式)。60分の窓に「78分の観測」を許すのはクライアント側の`tol = max(15, min*0.5)`(§4)。

## 2. 【計測窓ズレの機序】60分→78分の具体的計算経路

**【事実】観測系が3つ併存している**:

| 系 | 実装 | 記録条件 | 許容窓 |
|---|---|---|---|
| A. クライアント `view_snaps` | `yt-clicks.js:3898-3924` `captureSnaps_` | **その時アプリを開いていた時だけ** | `tol = max(15, b.min*0.5)`(`:3910`)= b60なら**[60,90]分** |
| B. GAS `時点記録` | `gas/コード.gs:1844-1871` | `snapshotStats` 10分トリガー(`:1790`) | `tol=9`分(`:1859`)= [60,69]分 |
| C. GAS `snapshot.gs`(再生数_スナップショット) | `gas/snapshot.gs:196-315` 30分トリガー・ティア式 | サーバー | **フロントは一切読まない**(表示に不使用の並行系) |

**78分の発生経路(事実)**:
1. 投稿から78分後にChamiがアプリを開く。
2. `captureSnaps_`: b60の窓は[60, 60+30]=[60,90] → `ageMin=78`で`inWin`成立(`:3911`)。
3. `if (!cur) rec[b.key] = {v:…, ageMin:78}`(`:3915`)= **初観測で永久固定**(以後、より窓に近い観測が来ても上書きしない)。
4. 表示は v584 の `pickBucketRec`(`rank-core.js:83-99`)が「目標60分に近い側」を選ぶが、**GAS側(系B)に記録が無いと比較相手がおらずローカル78分がそのまま主**になる。

**GAS側に記録が無い(=78が生き残る)条件(事実)**:
- **12時間/48時間窓と導線2(ピンク矢印)**: サーバーは`TIME_BUCKETS`6個のみ(`gas/コード.gs:1806`)・クリックは導線1のみ(`:1863`)。b720窓のローカル許容は+360分=**「12時間」の窓に最大18時間時点の値が出る**。
- **`post_id`が空の行**は時点記録の対象外(`:1854`)。
- **窓ミスの構造**: 許容9分 < トリガー周期10分 → 周期が完璧でも**約1割の窓は素通り**(前回実行が59.5分・次回69.5分だと[60,69]を跨いで両方失格)。GASの`everyMinutes`は数分ドリフトするので実際の取り逃しはもっと多い【周期の実測は未確認】。
- **トリガー総実行時間クォータの疑い【推測】**: `snapshotStats`は10分毎に短縮Workerへコード数ぶん`UrlFetchApp`+`Utilities.sleep(80)`(`:1567-1570`)を回す。コード数が増えるほど1回が長くなり、無償アカウントのトリガー実行時間上限(90分/日)に当たると**トリガーが黙って落ちて時点記録が丸ごと止まる**(→V5で実行ログ確認)。

つまり「78分」は**系Aの緩い窓(+50%)で採った観測が、系Bの欠測により主のまま表示される**現象。v584は「両方あるとき近い方を選ぶ」までは直したが、**「緩い観測をそもそも作らない」「系Bを欠測させない」は未着手**。

## 3. 【恒久対策】設計

方針: **「表示の正本」と「計測の正本」をそれぞれ1つに定め、acc1/acc2は同じ関数に引数`a`を渡すだけの完全対称にする**。既存の`設計書_投稿履歴シート正本化_2026-07-22`の完遂に相当する(当時「表示専用マージ」で止まった部分を最後まで)。座標系(1080×1920比率・CLAUDE.md §3)には一切触れない(このクラスタはCanvas非関連)。

### 3.1 供給一本化(症状1・2・3の恒久)

**設計**:
1. **供給関数を1本に**: `channelItemsFor_(a)`を唯一の供給元とし、`displayItems_()`は`channelItemsFor_(acct())`の薄い別名にする。`_sheetExtraCache`と`_rankSheetCache`を廃止し、**チャンネル別の単一キャッシュ**(`sheetCache[a] = {at, items}` + 永続SWR=既存`sheet_hist_raw__<a>`)へ統合。取得関数も`fetchSheetFor_(a, cb)`の1本(履歴もランキングも同じ物を読む=二重GAS往復の解消で症状2-Aも軽くなる)。
2. **`limit:300`の頭切りを廃止**: GAS `historyItems_`に`since`(投稿日時)/`offset`ページングを足し、クライアントは全量を分割取得して`sheet_hist_raw__<a>`に全量を保持。応答に`total`行数を含め、**「受信件数 < total」なら画面に「取得中(n/total)」を出す**(サイレント欠落の禁止)。
3. **fail-openの規律をローカル行にも統一**: `filterOtherChannel_`のローカル行判定(`:291-292`)を`_fromSheet`行と同じ「**別chと積極確定できた時だけ隠す**」に統一。歴史的シグナル(acc1-接頭辞・5mgl.com)単独では隠さない・動かさない。`sanitizeOwnership_`も同基準(DID確定のみ移送)へ。
4. **退避保存の失敗を可視化**: `persistSheetRaw_`のcatchで計測ヘルス(`_health`)へ「退避失敗(容量)」を出す。あわせて容量食いの`yt_meta_cache`等に上限(LRU)を入れる。
5. **パリティ不変条件テスト**(改修β依頼④の機械化): Nodeテストで「同一のシート応答を与えたとき、acc1とacc2で表示件数・除外理由が一致する」「供給関数内に`acct()`直参照が無い(引数`a`のみ)」をCIで検査。

**受け入れ条件**:
- [ ] acc2タブの表示件数 = 記録_ch2の非空行数 ±(ローカル下書き・手動行)が、**シート行数がいくつでも**成立(300行超で試験)。
- [ ] 機内モード(GAS全断)でリロードしても、直前に見えていた両chの全行が表示され続ける(SWR)。
- [ ] acc1↔acc2をタブ切替しても、それぞれの「最古の表示行」がシートの最古行と一致する。
- [ ] `git grep "acct()" yt-clicks.js` の結果に供給関数(fetch/merge/filter系)が含まれない。
- [ ] 既存のINC-112防壁(シート応答をshort_hist__へ書き戻さない)を維持=書き戻しコードを追加しない。

**実装手順(別便・Opus以下)**:
1. `fetchSheetExtra_`/`fetchSheetForRank_`→`fetchSheetFor_(a)`へ統合(既存テスト`tests/test_hist_merge.js`を先に回す)。
2. `displayItems_`を`channelItemsFor_(acct())`+`filterOtherChannel_`に置換。
3. GASへ`since`/`offset`/`total`追加(GAS_VERSIONバンプ・`GASを反映.bat`)。クライアント分割取得。
4. `filterOtherChannel_`ローカル行のfail-open化+`sanitizeOwnership_`のシグナル降格(移送はDID確定のみ)。
5. パリティ不変条件テスト追加 → `node scripts/bump.mjs`で一括バンプ。

### 3.2 計測一本化(症状4の恒久)

**設計**: **正本=GAS`時点記録`**。クライアント観測はサーバー未対応領域の補助に降格。
1. **サーバーを全窓・全導線対応に**: `TIME_BUCKETS`へ`[720,'12時間'],[2880,'48時間']`を追加し、`captureTimepoints_`へ導線2クリック(`wcode`は`snapshotStats`が既に取得済み `gas/コード.gs:1569`)の列を追加。
2. **固定許容窓→補間へ**: 10分毎スナップの前回値と今回値から、**バケット境界時刻ちょうどの値を線形補間して記録**する(`経過分(実測)`は公称値そのもの、補間フラグ列を追加)。これで公称60分=記録60分(±0)、トリガーがドリフトしても成立。窓ミス(9分<10分問題)も消える。
