# 診断 — 作成履歴サムネの同期detox(go5_stock_archive の thumbDataUrl 恒久縮退・2026-08-18・Fable5設計/C-043)

C-043準拠=原因確定と安全な実装計画のみ(コードは書かない・実装は別担当)。前提の止血
(`writeMetaResilient_` stock.js:129 / `writeArchiveResilient_` stock.js:204)は**壊さない**。
Chami最重要不変条件=**完了作品(作成履歴のitem)を1件も失わない**(2026-08-03裁定・墓標なしunion)。

---

## ① 原因の一段深い確定(実物読了に基づく)

### ①-1 箱を埋める実体は「作成履歴×2倍」
- `go5_stock_archive`(ARCHIVE_MAX=30・stock.js:15-16)は item ごとに `thumbDataUrl`(≤160KB・saveStock_ stock.js:752-757 で同梱)を抱える=単体で最大約4.8MB。
- **さらに同じ中身が `sync2_snap` にもう1部入る**。syncOnce の persist(sync.js:862)は
  `saveSnap({ls:newSnapLs,…})` で **マージ後のLS全値(=作成履歴のフル配列・thumb込み)を localStorage
  `sync2_snap` へ複製保存**する(sync.js:211-212)。つまり iOS Safari の約5MB箱に対し、作成履歴は
  **実効ほぼ2倍(最大約9.6MB相当)の圧**をかける。これが「thumbを数件剥がした程度では逼迫が解消しない」
  一段深い理由。ドラフト(go5_stock_meta・20件×160KB=3.2MB)も同じ二重計上構造。
- 副作用としてpush本文(`pushState` sync.js:141-144 の blob)も肥大し、sync-worker の
  `too_large`(「同期データが上限を超えています」sync.js:130)で**同期全体が落ちるリスク**まで抱える
  (落ちると作成履歴だけでなく全キーの伝播が止まる)。

### ①-2 「剥がしても remote から戻る」機構の確定
- 雲の実体は**キー別ストアではなく1枚のJSON blob(whole-blob CAS)**。push はマージ結果 `mls` を丸ごと
  送って置き換える(sync.js:846,864)。**union は完全にクライアント側**で行われる。
- その union は `arrIdField_`(sync.js:359)→`unionByField`(380)→`mergeCandItem_`(366)の
  **id単位フィールドunion**。`isEmptyVal_`(361)により「空(undefined/null/"")で非空を消さない」。
  よってローカルで thumbDataUrl を剥がした item(フィールド欠落=空)と、remote(older)の thumb持ちitem が
  同id で合流すると、**mergeCandItem_ が older の thumb を保持**(sync.js:375 のコメント通りの正常動作)。
- マージ結果はローカルLSへ書き戻され(sync.js:800-801)、push対象 `mls` にも反映される(796)。
  → `writeArchiveResilient_` の剥がしは**最長60秒(AUTO_MS)以内に自動で巻き戻る**。局所止血が根治に
  ならない、の機構的確定。

## ② 案2の安全設計 — 3案比較と推奨

課題の本質は「**削除しないunionの世界で、特定フィールドだけを全端末で確実に痩せさせる**」こと。
比較検討した3案:

### 案A: sentinel(thumbDataUrl:"" を「明示クリア」として非空扱いで上書き)
- 仕組み: `mergeCandItem_`/`isEmptyVal_` の意味論を「archive の thumbDataUrl に限り "" は明示クリア」
  に変える。
- **不採用理由(リスク過大)**:
  1. `mergeCandItem_` は cand_items / go5_stock_meta / bsky_tpl_book / bsky_discount_urls /
     cand_text(mergeCandTextRec_ sync.js:337)**全部の共有マージ核**。「空で非空を消さない」は
     2026-07-30「作品URL消失」の恒久ガードそのもの。キー/フィールド文脈を `unionByField`→
     `mergeCandItem_` の全呼び出し(6箇所以上)へ引数で貫通させる改修=回帰面が最大。
  2. **版混在で壊れる**: 旧?v=のJSを積んだ端末は "" を空として扱い、older の thumb を保持して
     フル配列を丸ごと push(whole-blob)→ sentinel 自体が雲から消え、剥がしが白紙に戻る。
  3. sentinel(空文字フィールド)が全itemに恒久残留するノイズ。

### 案B: 専用 thumb-slim 台帳(`go5_thumbslim_v1`: id→slimTs・mergeDelMap型union・SYNC_ALLOW登録)
- 仕組み: 「このidのthumbは剥がし済み」を墓標類似の同期台帳で伝播し、union後に該当idの
  thumbDataUrl をフィールド削除する。
- 成立はする(itemは消さない)が、**決定的な欠陥が1つ**:
  台帳への記帳は**もう1本のlocalStorage書き込み**。剥がしが発動するのはまさに
  QuotaExceeded の瞬間(`writeArchiveResilient_` の縮退パス)で、**その瞬間に台帳書き込み自体が
  quota で失敗し得る**=記帳漏れ→remote から復活、の穴が構造的に残る。
  加えて: 新同期キーの SYNC_ALLOW 登録・sync側の新マージ分岐・台帳のGC/TTL・restoreStock_ との
  整合(復元時に台帳を消すか)と、可動部が多い。

### 案C(推奨): 決定的正規化「thumb budget」— 台帳もsentinelも不要
- **純関数 `slimStockArchive(arrStr, keepN)` を1本だけ**core/sync.js に置く(単一ソース原則):
  - `completedTs||ts` の降順(同値はid降順で決定的にタイブレーク)で**新しい keepN件(=3)だけ
    thumbDataUrl を残し、それ以外の item から thumbDataUrl フィールドを削除**。
  - **itemの追加・削除・並び替えは一切しない**(配列順は保持・消すのはフィールド1個のみ)。
  - parse失敗/非配列は**入力をそのまま返す**(fail-open・nullを返さない=LSへnullが入る事故を封じる)。
- **適用点は2箇所**(両方が同じ関数を呼ぶ):
  - (a) sync.js の作成履歴マージ分岐(isStockArchiveKey・applyTombstone 直後=772行の次)で
    `finalV = slimStockArchive(finalV, 3)`。→ LS書き戻し(800-801)と push対象 `mls`(796)の両方が
    痩せた値になる。
  - (b) stock.js の `saveArchive`(223)= `writeArchiveResilient_` へ渡す**前**に常時プリスリム
    (quota失敗を待たずに毎回痩せて書く。既存の段階縮退はそのまま最終防衛線として残す=壊さない)。
- **なぜ古いthumbが remote から消えるか**: 雲は whole-blob 置換(①-2)。新JSの端末が1回でも
  push すれば、痩せた配列が**雲の唯一の正**になる。別端末のローカルに残る thumb は次のマージで
  union復活するが、その端末も (a) で剥がしてから書き戻し/pushする=**不動点
  slim(union(x, slim(x))) = slim(x) に収束**。per-id の複製状態(台帳/sentinel)が要らないのは、
  「どれを剥がすか」が**既に同期済みのタイムスタンプから全端末で同一に計算できる**から。
- **不変条件の担保**: union・墓標(go5_stock_arch_del)・restoreStock_ の意味論は無変更。
  slim はフィールドを消すだけで id 集合に触らない=「完了作品が消えない優先」を構造的に侵せない。
- **版混在の過渡**: 旧JS端末が生きている間はその端末の push で雲が一時的に太り得る(=現状維持と同じ。
  データ喪失は無い)。新JS端末の次の push で再度痩せる。全端末が ?v= バンプ後のリロードを終えれば
  収束(bump.mjs 一括バンプ+CIスモークが前提を保証)。
- 効果見積: インライン thumb 最大 30×160KB≒4.8MB → 3×160KB=480KB。sync2_snap の複製込みで
  実効約9.6MB→約1MB弱。push本文も同幅で痩せ、too_large リスクも同時に下がる。

**推奨=案C。** 案Bは「quota逼迫の瞬間に台帳書き込みが要る」自己矛盾があり、案Aは共有マージ核の
意味論変更で回帰面が最大。案Cは新規の同期状態ゼロ・可動部1関数・不変条件を構造的に満たす。

## ③ thumb剥がし後のサムネ表示復元経路の確認ポイント

表示は render(stock.js:1780-1818)の単一チェーンに集約済み(作成履歴カード renderArchItem_ も同じ
thumbFor を受ける・stock.js:1768):
`_thumbCache` → `m.thumbDataUrl` → IDB `stock_t_<id>` → IDB `stock:imgs:<id>`(th/prev/src) →
IDB `stock_prev_/stock_img_` → R2 `go5src:<id>`(1回だけ・_r2ThumbTried)。

確認ポイント(実装後に実物で見る):
1. **archive item の blob は生きている**: archiveStock_(884)は blob を消さない。delBlobs_(278)が
   走るのは ARCHIVE_MAX 溢れ(896-897)と purge(931)のみ。→ 剥がした古いitemも同一端末では
   `stock_t_<id>` から出る。
2. **2台目は stock:imgs ミラーで出る**: `stock:imgs:` は同期IDBレールに載っている(実物確認済=
   sync.js:55-56 `SYNC_IDB_PREFIXES` に "stock:imgs:" あり)。ensureBlobMirror_(312)が th/prev/src を
   後追い補完する。→ 2台目の作成履歴サムネはミラー経由で表示。
3. **既知の残穴(今回スコープ外・P3として記録)**: チェーンは `if (!store) return null`(1787)で
   IDB不能端末を早期リターンするため、**IDBが完全に死んだ端末では R2 go5src フォールバック
   (1806-1811)に到達しない**。剥がし済み古itemは灰色プレースホルダになる。許容(古い完了作品・
   文字情報は全部残る)だが、必要なら「R2 try を store ガードの外へ出す」小スライスを別途提案。
4. 受け入れ観察: 作成履歴を開き(details 1764-1770)、剥がし対象の古いitemでもサムネ画像が出る/
   最悪でも灰色箱+題名・完了日時・YouTubeリンクが揃っていること。

## ④ test-must-fail 純関数テストの対象(tests/test_archive_slim.js 新設・test_sync_tombstone.js と同様式)

`core/sync.js` の `_test` へ `slimStockArchive` を追加公開(既存 _test 群 sync.js:1008 と同列)。
各テストは**入力差し替えで必ず落ちること**を追加時に1回実証する(test-must-fail 手順に従う。
空PASS禁止):

1. **mergeで完了作品itemが消えない**: `unionByField(A, B, "id")` に互いに無いidを与え、
   全id が結果に居る。→ 差し替え(片側のidを結果期待から抜く/union実装を丸ごと置換したと仮定した
   入力)で fail することを確認。既存 test_sync_tombstone.js:98-106 の拡張でよい。
2. **slimはitem本体を消さない・並びを変えない**: 5件(全部thumb持ち・completedTsばらばら)→
   `slimStockArchive(x,3)` で id集合・配列順・thumb以外の全フィールド(title/youtubeUrl/account等)が
   完全一致、thumbDataUrl は新しい3件だけ残る。→ 期待側を「4件残る」「1件消える」に差し替えて fail 確認。
3. **sentinel問題の再現と根治の証明(復活→不動点)**:
   `local = slim(x)`(剥がし済み)と `remote = x`(古thumb持ち)を union →
   (3a) **thumbが復活していること**をassert(=罠が実在する証明・これが落ちたら意味論が変わった合図)。
   (3b) その結果に slim を掛けると古thumbが**実際に消え**、`slim(union(slim(x), x)) === slim(x)`
   (不動点=収束)をassert。→ slim を恒等関数に差し替えると (3b) が fail することを確認。
4. **墓標との合成でitemを失わない**: `applyTombstone → slim` の順で、purge対象以外の id が
   1件も減らない(completedTs>削除ts の正当復活も残る)。
5. **fail-open**: 壊れたJSON/非配列/空文字入力で slim が**入力をそのまま返す**(nullや例外を出さない)。
   → 実装を「catchでnull返し」に差し替えると fail することを確認。

## 最大リスクと監視点
- **最大リスク**: S3 のマージ分岐は全キー共通ループ内。分岐条件を isStockArchiveKey に限定し損ねると
  他キー(候補/テンプレ/ドラフト)のフィールドを剥がす。→ ④-2/④-4 のテストと、S3 レビュー時に
  「slim 呼び出しが isStockArchiveKey ブロック内にのみ存在する」を目視+grepで確認(grep語= slimStockArchive)。
- 版混在の過渡で雲が一時的に太る(②案C末尾)=データ喪失ゼロ・自己回復。監視は S3 受け入れの
  「60秒放置後も復活しない」で足りる。
