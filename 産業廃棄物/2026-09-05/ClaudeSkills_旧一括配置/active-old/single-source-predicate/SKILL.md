# 判定式は1か所に置く

## なぜ要るのか
改修ログのうち **14件**が「同じ判定を複数経路が各自持っていて食い違う」型。
直近の実例= AI判定が **候補バッジ / 候補→作成(`applyGenres`) / 作品URLフェッチ(`autoApplyAttrsFromInfo_`)**
の3経路で各自の式を持ち、同じ作品が経路によって別の答えになっていた
(`e55b4c8` で `core/movie-attrs-core.js` へ一本化・v=759)。

★**症状は「片方だけ直る」。** 直したのに再発する時は、**真因が別の経路に在る**と疑う。

## 手順

1. **書く前に数える。** 同じ判定が既に在るかを grep する。
   例= `grep -rn "isAI\|onSale\|候補" --include=*.js core/ *.js | head -40`
   ★**無いと言う前に実際に探せ。**大抵もう在る。
2. **在ったら、そこへ寄せる。** 新しい式を足さない。既存の純粋関数を import して使う。
   このプロジェクトの正本置き場= `core/*-core.js`(`util.js` / `account.js` / `storage-keys.js` /
   `movie-attrs-core.js` / `affiliate-core.js` / `bluesky-core.js` / `verify-core.js`)。
3. **無いなら、純粋関数として `core/` に新規で作る。** 引数と戻り値だけで決まる形にする
   (DOMやlocalStorageを読まない=テストできる形)。
4. **★呼び出し元を全部数えて、全部差し替える。** 1か所でも残ると、そこが次の食い違いになる。
   「この経路は別なので影響なし」と書きたくなったら、**その主張こそ数え直す**。
5. **`tests/` に純粋関数のテストを置く**(`test-must-fail` の手順で落ちるのを1回見る)。
6. フロントを触ったら **`node scripts/bump.mjs` で `?v=` を一括バンプ**。
   ★手で個別に上げるとCIが赤になる(2026-07-20に5版が混在しpush6回すべてfail)。

## 判定の目安(全部を一本化しない)
- 寄せる= **同じ問い**に答えている(「これはAI作品か」「セール中か」「どのアカウントか」)。
- 寄せない= 見た目が似ているだけで**問いが違う**もの。無理に共通化すると引数が増えて別の穴になる。
- ★**共有される関数に条件を足す変更は、呼び出し元を全部数える**(足した瞬間に全経路の挙動が変わる)。

## 既に一本化済みのもの(勝手に増やさない)
- アカウント解決= `core/account.js`。**`current_account` の直読み・`acc1` フォールバックはここ1箇所だけ。**
- localStorageキーの分類・同期可否= `core/storage-keys.js`(**許可リスト方式**。新キーは既定で同期しない)。
- 台帳の ts の読み方= `scripts/lib/jsonl_store.ts_epoch()`(自前の `_parse_ts` を書かない)。
