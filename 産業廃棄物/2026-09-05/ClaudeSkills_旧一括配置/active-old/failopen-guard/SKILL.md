# 無言で死なせない(fail-open)

## なぜ要るのか
改修ログ736行のうち **32件**がこの型。**iOS Safari の IndexedDB は理由も言わずハングする。**
`await` が返ってこない/rejectする経路を「例外だから止める」で書くと、**画面が真っ白のまま何も起きない**。
Chamiの端末で起きる事故はほぼ全部この形をしている。

★原則= **可用性に関わる所は fail-open。判定不能なら「進む側/喋る側」へ倒す。最悪の事故は沈黙。**

## 型(この順で書く)

1. **タイムアウトを必ず持たせる。** 待ちっぱなしの `await` を書かない。
   源(ヘルパの中)でタイムアウトを付ける——呼び出し側ごとに付けると必ず漏れる。
2. **拒否・タイムアウトを「無い」として扱う。** 例= IDBの `get()` は失敗したら **null を返す**
   (例外を投げっぱなしにしない)。`d0b0008` で `get()` を源で fail-open にしたのがこの形。
3. **控えを見に行く経路を必ず用意する。** 例= `resolveVideoBlob_` は IDB が
   `idb-timeout` で reject した時に **R2の控えを見に行かず即エラーにしていた**ため
   「動画データの取得に失敗しました」が出ていた(`956d17e`)。**拒否時もフォールバックへ倒す。**
4. **失敗しても本業を止めない。** 例= Drive自動保存が失敗しても**動画作成は成功のまま**にする。
   台帳が書けなくても投函は止めない(`daily_reflection_trigger.py` の `_save_state` が同じ形)。
5. **黙って落とさない。** fail-open は「無かったことにする」ではない。
   **結末を残す**(ログ・台帳・画面のどれか)。★沈黙したまま倒れるのが一番悪い。

## やってはいけない
- **常に誤発火する安全網を足す。** 緊急用の例外が日常運用になった時点でそのガードは死んでいる。
- **mtimeのような「たまたま当たっている値」に生死判定を乗せる。** 生死そのものを見る。
- **自分が直前に入れたガードが検証経路を潰していないか**を確かめずに次へ行く
  (検証が失敗したら、まず**検証の妥当性**を疑う。実装はその後)。

## 検査
- `node tests/test_idb_failopen.js`(拒否・タイムアウト時に倒れる先を固定している)。
- 新しく fail-open を足したら **`test-must-fail` の手順で「落ちること」を1回見る**。

## 逆に fail-closed にすべき所(混ぜない)
- **不可逆な操作**(削除・上書き・外部への書き込み・載せ替え)は、判定不能なら**待つ側**へ倒す。
  例= `reload_keeper.py` は「暇か判定不能(None)」を暇とみなさず必ず待つ。
- 見分け方= **間違って進んだ時に取り返しがつくか。** つくなら fail-open、つかないなら fail-closed。
