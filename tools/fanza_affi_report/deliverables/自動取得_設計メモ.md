# 自動取得 設計メモ — 🐧さん向け FANZA/DMM日次売上レポート自動配送の運転アーキテクチャ

- 作成日: 2026-09-02 / 作成: 設計思考担当(ADAFI事業)
- 位置づけ: **実装前の設計書**。一本化先 `tools/fanza_affi_report/` に何をどう足すかを、Q2の答えが返る前に両腕とも確定させておく。
- 前提(確定事実): DMM管理画面に売上APIは無い・定期メール機能も無い → **CSVエクスポート自動化が唯一の道**。CSVは cp932・7列(サービス/品番/商品タイトル/販売金額/報酬体系/報酬件数/報酬額)・日付列なし・クリック数なし。🐧さんに頼めるのは「最初のログイン1回」「スクショ/アドレス貼り」まで。
- 機密の扱い: ログイン資格情報・実URLは🐧さんのPCの `config.ini` のみ。本メモは全てプレースホルダ表記(`<...>`)。

---

## 0. 分岐の判定基準(1文)

**Q2の答えが「一度ログインすればしばらく入ったままでいられる」なら腕A、「毎回SMSの数字やパスワード入力を求められる」なら腕Bを選ぶ。**

補足: 「パスワードは毎回だがSMSは初回だけ」等の中間回答は、まず腕Aで実地検証し(保存セッションで翌日もCSVが取れるか3日試す)、取れなければ腕Bへ落とす。腕Bはいつでも成立する安全側の腕であり、腕A運転中の恒久フォールバックでもある(mode切替1行で移行できるよう共通の土台に作る)。

## 腕A: セッション保持される場合(保存セッションで日常自動取得)

### A-1. データフロー(段)

```
[毎朝 タスクスケジューラ] → run_report.py
  段1 取得    : session_dir の永続プロファイル(Cookie)を headless Playwright の
                context.request で再利用し、<CSVエクスポートURL> を直叩き → CSVバイト列。
                ブラウザ画面は出ない。直叩きが構造変化で失敗する場合のみ、
                同セッションで <レポート画面URL> を開き <CSVエクスポートのボタン> を
                クリックしてDL(第2層フォールバック)。
  段2 失効判定: HTTP 401/403 または最終URLがログイン画面 → SessionExpired として即・失敗系へ
                (「再ログインを1回お願いします」の通知。自動でID/PWを打たない)。
  段3 検証    : cp932デコード → 0バイト/HTML混入/ヘッダ不一致/数値変換失敗を弾く。
                ヘッダのみ(明細0行)は「売上ゼロの正常」として通す。
  段4 集計    : 報酬体系ごとの件数・金額 + 合計(aggregate)。
  段5 前日比  : state/daily_summary.json の直近保存日と比較。初回は「前回データ無し」。
  段6 整形    : 本文=軽い要約(体系別+合計+前日比)。グラフ化はツール外(Chami後工程)。
  段7 配送    : Discord Webhook(本文 + CSV原本ファイル添付)またはメール。
  段8 記録    : 送信成功後にのみ state を record(送れなかった日を「前日」にしない・既存仕様)。
                加えて last_success_date を記録(沈黙検知用)。
[例外時] 初回・失効時のみ: relogin(実Chromeが開く → 🐧さんが手でログイン、2FAも人が通す
         → 「ログイン状態を保持」にチェック → セッションが session_dir に保存される)。
```

### A-2. config.ini のキー(腕A)

| セクション/キー | 値(プレースホルダ) | 備考 |
|---|---|---|
| [report] title | FANZAアフィ売上レポート | 既存 |
| [input] csv_dir / csv_glob / encoding | `<保存先フォルダ>` / *.csv / cp932 | 既存。DLしたCSVの保管先 |
| [output] sender / webhook_url | discord / `<WebhookのURL>` | Q5で確定 |
| [state] path / [log] path | 既定のまま | 既存 |
| [download] mode | **session**(新設値) | 腕Aの心臓 |
| [download] session_dir | sessions | 新設。永続プロファイル置き場 |
| [download] report_page_url | `<いつも見ている画面のURL>` | 新設。Q1。失効判定の起点 |
| [download] export_url_template | `<CSVエクスポートの実URL(期間パラメータ入り)>` | 新設。Q3+DevToolsキャプチャ1回 |
| [download] login_url | `<ログイン画面のURL>` | relogin時に開くだけ |
| [download] csv_export_selector | `<エクスポートボタンのセレクタ>` | 第2層フォールバック用のみ |
| [download] browser_channel | chrome | 新設。Q4で chrome/msedge 確定 |
| [schedule] period | yesterday | 新設(penguinから移植)。当日分は翌日反映のため |

**腕Aで不要になるもの**: `username` / `password`(configに書かせない。ログインは常に人がブラウザで行う=資格情報がファイルに残らない)、`username_selector` / `password_selector` / `login_submit_selector`(自動フォーム入力をしないため)。現行の PlaywrightDMMDownloader(毎回ID/PWでフォームログイン)は2FAで破れる前提なので腕Aでは使わない。

### A-3. 常駐の形(Windowsタスクスケジューラ)

- タスク1(日次本体): 毎朝 `<例 07:30>` に `python run_report.py` を起動。開始ディレクトリ=ツール直下(config.ini を相対で拾う・既存README仕様)。
  - 「スケジュールされた時刻にタスクを開始できなかった場合、すぐにタスクを実行する」= ON(朝PCが点いていなくても起動後に走る)。
  - 「タスクを要求時に実行中の場合」= 新しいインスタンスを開始しない。
  - 失敗時の再試行: 10分間隔で3回(タスクスケジューラ側設定)。ツールは冪等(同日2回目の成功送信を防ぐため state の last_report_date が今日なら要約を再送しない、を新設)。
  - 実行条件は「🐧さんがログオンしているとき」を基本とする(ログオフ実行はChromeプロファイルのロック/描画で壊れやすい。素人PCでは単純さ優先)。
- タスク2は作らない(失効検知は日次本体の段2に内蔵。失効した日は失敗通知が出て、🐧さんが relogin.bat をダブルクリック=年数回想定)。
- 配布形: PyInstaller単一exe + config雛形 + relogin.bat + セットアップ手順1枚(既存方針)。

### A-4. 静かな死/取得失敗の検知と通知

- 原則: **毎実行は「成功レポート」か「失敗通知」のどちらか一方で必ず終わる**(無言終了のコードパスを作らない)。fail-open=判定に迷ったら(CSVが怪しい・構造変化疑い)成功扱いにせず、喋る側(失敗通知)へ倒す。
- 失敗通知には分類を付ける(penguinのFailureKindを移植): セッション失効 / 構造変化疑い / CSV異常 / ネットワーク障害 / 配送失敗 / 不明。分類ごとに「次にやること」1行を添える(失効→「reloginを1回実行してください」)。
- 送信側で検知できない死(タスク未起動・PC電源断・Python起動前のクラッシュ)は**受信側警報**で拾う: 受け側(Chami側)の鮮度警報(producers.json 登録制)に「毎朝 `<例 09:00>` までに未着なら警報」を登録する。送信側では原理的に検知不能(既存penguin README方針)。
- 補助: state の last_success_date を見て、成功時レポート本文に「前回成功から2日以上空いた」旨を自動追記(欠測をレポート自身が申告する)。

### A-5. 取得失敗と売上ゼロの区別

- 売上ゼロ(正常): CSVがヘッダのみ・明細0行 → 通常レポートとして「報酬合計 0円」を送る。
- 取得失敗: DL不能 / 0バイト / HTML混入(ログイン画面が200で返る) / cp932デコード失敗 / ヘッダ不一致 → 件名 `[取得失敗]`、本文1行目「※これは売上ゼロではありません。取得エラーのため金額は不明です」。金額の記載自体を出さない(既存fanza_affi_report仕様を踏襲)。
- 取得失敗の日は state に record しない(前日比の基準を汚さない・既存仕様)。

## 腕B: 毎回2FA/SMS必須の場合(mode=local / 監視フォルダ方式)

自動ログインは諦める。🐧さんの負担=**朝いつも通りログインしてCSVをダウンロードするだけ**(1日1回)。以降の整形・前日比・配送は全自動。

### B-1. データフロー(段)

```
  段0 人手    : 🐧さんが朝、管理画面からCSVをDL → 所定フォルダ <監視フォルダ> に保存。
                ブラウザの既定DL先をそのまま監視フォルダにできれば「保存ボタンを押すだけ」。
  段1 監視    : タスクスケジューラが <例 08:00> から15分間隔で run_report.py を起動
                (常駐プロセスやwatchdogライブラリは使わない。ポーリング型が素人PCで最も堅い)。
  段2 当日判定: csv_glob に合う最新ファイルの更新時刻(mtime)が「今日」か、かつ
                前回処理済みファイルとハッシュ不一致か、で「今日の投函あり」を判定。
     ├ 投函あり → 段3へ。処理後は processed/ へ移動(二重処理防止・フォルダも綺麗に保つ)。
     ├ まだ無し(締切前) → 何もせず静かに終了(次の15分後の起動に任せる)。
     └ 締切 <例 11:00> を過ぎても無し → 「未投函」通知を送って当日は打ち止め(下記B-4)。
  段3以降    : 腕Aの段3〜段8と完全に同一(検証→集計→前日比→整形→配送→記録)。
  同日2回目以降の起動: state の last_report_date が今日なら即終了(no-op・冪等)。
```

### B-2. config.ini のキー(腕B)

| セクション/キー | 値(プレースホルダ) | 備考 |
|---|---|---|
| [report] title | FANZAアフィ売上レポート | 既存 |
| [input] csv_dir | `<監視フォルダ 例 Downloads配下>` | 既存キーをそのまま監視対象に転用 |
| [input] csv_glob / encoding | *.csv / cp932 | 既存 |
| [output] sender / webhook_url | discord / `<WebhookのURL>` | Q5で確定 |
| [state] path / [log] path | 既定のまま | 既存 |
| [download] mode | **local**(既存値) | 腕Bの心臓 |
| [watch] deadline_time | 11:00 | 新設。これを過ぎて未投函なら通知 |
| [watch] processed_dir | processed | 新設。処理済みCSVの退避先 |
| [watch] require_today | true | 新設。mtimeが今日のファイルだけを対象にする |

**腕Bで不要になるもの**: [download] のセレクタ群全部・username/password・session_dir・export_url_template・report_page_url・login_url。**Playwrightのインストール自体が不要**(pip不要・単一exeが軽い・素人PCへの導入障壁が最小になる。これが腕Bの隠れた利点)。

### B-3. 常駐の形(Windowsタスクスケジューラ)

- 1本のタスクを「毎日 `<例 08:00>` 開始、15分間隔で繰り返し、継続時間4時間(締切まで)」で登録。
- 「開始時刻を逃したら即実行」ON / 多重起動は「開始しない」 / 実行条件=ログオン時。
- 失敗時の扱い: ツールは冪等なので再試行は仕組みに任せる(次の15分後の起動が実質リトライ)。配送失敗(Webhook不通)だけはその回の起動で失敗通知を試み、state未記録のまま次回に持ち越す。

### B-4. 静かな死/取得失敗/未投函の検知と通知

- 腕Aの原則(成功か失敗通知のどちらかで終わる・fail-open)は同じ。加えて腕B固有の**第三の状態=「未投函」**を設ける:
  - 締切時刻を過ぎても今日のCSVが無い → 「今日の分のCSVがまだ届いていません。管理画面からダウンロードして `<監視フォルダ>` に保存してください」を配送先へ送る(責めない文面・🐧さんへのリマインドを兼ねる)。1日1回だけ送る(15分ごとに連打しない)。
  - 古いファイルしか無い(mtimeが昨日以前・ハッシュが前回と同一)場合も「未投函」扱い(昨日のCSVを再集計して偽の当日レポートを作らない)。
- 壊れたファイルが投函された(HTML混入・文字化け・列不一致)→ 「未投函」ではなく `[取得失敗]` 系の文面(分類つき)。
- 受信側警報(未着ならX時に警報)は腕Aと同一で必須。腕BはPC電源断に加え「🐧さんの旅行・病欠」でも沈黙するため、受信側警報の価値がむしろ高い。

### B-5. 取得失敗と売上ゼロの区別

- 3値で扱う: **売上ゼロ**(ヘッダのみCSVが投函された=正常レポート「0円」) / **取得失敗**(投函されたが中身が異常=`[取得失敗]`文面) / **未投函**(ファイルが無い=リマインド文面)。
- 「未投函」と「取得失敗」を分けるのが腕Bの肝: 前者は🐧さんへの声かけ、後者はこちら(開発側)の調査事項であり、宛先と文面が違う。

## 6. penguin_report → fanza_affi_report への移植差分(土台に足すもの)

1. **二層取得(腕A採用時)**: `downloader.py` に SessionDownloader を新設 — `launch_persistent_context(session_dir, channel="chrome")` + `context.request` でエクスポートURL直叩き、401/403・login遷移で SessionExpired(penguin `fetch.DmmDashboardFetcher` 相当)。あわせて `relogin.py`(実Chromeで人手ログイン→永続プロファイル保存)を移植し relogin.bat 化。現行 PlaywrightDMMDownloader(毎回ID/PWフォームログイン)は腕Aでは非推奨に格下げ。
2. **静かな死検知(パース側)**: `parser.py` に penguin `csv_parser` の検証を統合 — 0バイト/HTML混入(ログイン画面が200で返る)/cp932デコード失敗を例外、ヘッダのみ=売上ゼロ正常。土台は「必須列が欠けたら例外」までは有るが、HTML混入・空検知が無い。
3. **失敗分類**: penguin `notify.FailureKind`(失効/構造変化/CSV異常/ネットワーク/配送失敗/不明)+分類ごとの「次の一手」1行を、土台の `_notify_failure` / `_notify_download_failure` 文面に付ける。
4. **CSV原本のファイル添付**: penguin `delivery.py` のDiscord Webhook multipart添付を `senders.py` へ移植(本文要約+CSV添付。グラフ化はChami後工程なので原本を届けるのが主目的)。
5. **state拡張**: `state.py` に last_success_date(沈黙の自己申告用)と last_report_date / last_file_hash(腕Bの冪等・未投函判定用)を追加。
6. **schedule/period**: penguin の period=yesterday 概念(当日クリックは翌日反映)を config に追加。
7. **テスト観点(penguin 22件グリーンの移植)**: 「HTMLが200で返る」「0バイト」「ヘッダのみ=ゼロ正常」「列構造変化」「配送失敗時に失敗通知が出る」「パイプライン一気通し(ネット不要のダミーcp932)」を `tests/` へ移植。腕B新設分として「未投函判定(mtime当日/ハッシュ同一)」「同日冪等」を追加。
8. **受信側警報の登録(ツール外)**: 「毎朝X時までに未着なら警報」をChami側の鮮度警報(producers.json 登録制)へ登録する運用手順をREADMEに1行追記。

移植完了までpenguin_reportは消さない(既存方針どおり参照退避)。

## 7. 🐧さんの答え(Q1-Q5)→ configキー対応表

| 質問 | 腕Aで入る先 | 腕Bで入る先 |
|---|---|---|
| Q1 いつも見る画面のURL | [download] report_page_url(+ login_url) | 不要(🐧さん向け手順書に載せるだけ) |
| Q2 セッションが続くか | **mode=session を選ぶ根拠** | **mode=local を選ぶ根拠** |
| Q3 CSVボタンの画面+URL | [download] export_url_template(DevToolsで実リクエストを1回キャプチャして確定)+ csv_export_selector(フォールバック) | 不要(手順書のスクショ素材に使う) |
| Q4 OSとブラウザ | タスク登録書式(Windows=タスクスケジューラ / Mac=launchd)+ [download] browser_channel(chrome/msedge) | タスク登録書式のみ |
| Q5 届け先 | [output] sender=discord(または mail)+ webhook_url=`<実値>` | 同左 |

Q2の答えが返った瞬間にやることは「mode の1行を session か local に書く」だけ。他のキーはどちらの腕でも上表どおり機械的に埋まる。

## 未確認で設計が確定しない点(3つ以内)

1. **Q2そのもの**(セッション保持の有無)= 腕の分岐。返答1つで mode が確定する。
2. **CSVエクスポートの実リクエスト形**(URL直叩きが可能か・CSRF/期間パラメータの有無)= Q3のスクショ+実アカウントでのDevToolsキャプチャ1回で確定。直叩き不可でも csv_export_selector クリック方式(第2層)で腕Aは成立する。
3. **🐧さんPCの朝の運用実態**(何時に起動しているか・ブラウザ既定DL先を監視フォルダにできるか)= タスクの開始時刻・締切時刻・csv_dir の実値が確定する。Q4の答えに一言ヒアリングを添えて埋める。
